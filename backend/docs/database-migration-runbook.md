# PostgreSQL migration and Railway cutover

Status: **BLOCKED until operator inventory, restore rehearsal, verification and
explicit cutover approval are recorded.** Repository changes do not configure
Supabase, Railway, Redis, DNS or production secrets. Never use destructive tests
against production, the source, or a rehearsal copy of production data.

## 1. Record the source and destination

1. Record the deployed source application commit, provider, PostgreSQL version,
   database/schema names, migration revision and maintenance contacts. Confirm
   that this checkout matches the deployed API contracts.
2. Determine the API hostname actually used by deployed Android clients. A
   provider hostname embedded in an APK cannot be migrated by changing your DNS.
   Do not retire the old endpoint until a tested client transition exists.
3. Confirm that Android enforces cached policies during airplane mode, backend
   outage and device restart. Confirm how queued events are replayed. No Android
   code or event-upload API exists in this checkout; these are external evidence
   requirements, not implemented features of this change.
4. Create separate Supabase production, rehearsal/staging and disposable test
   projects. Do not use a production copy for destructive test execution.
5. Choose PostgreSQL versions/extensions compatible with the source. Inventory
   all non-system schemas; the supplied detailed verification covers `public`
   EduG tables. Additional application schemas need an expanded reviewed scope.
6. Review the historical-secret incident described in `production-runbook.md`.
   Confirm revocation/rotation with the credential owner. Preserve valid current
   signing/audit keys and pairing-pepper versions across transfer. An approved
   audit-key rotation changes pseudonym continuity; retain controlled historical
   key/version records and never rewrite evidence.

## 2. Configure Supabase securely

1. In the target dashboard, open **Connect** and copy the **direct connection**
   settings into the approved secret manager. Use port 5432. No credentials go
   into source, chat, a frontend environment, or a shell command argument.
2. In database settings, enable SSL enforcement before loading production data;
   this may restart the target database. Download the target CA certificate and
   make it available to the runtime and migration runner. Use `sslmode=verify-full`
   and `sslrootcert` where the certificate is not in the system trust store.
   For a file-based CA: create `backend/certs`, save the dashboard's public CA
   as `supabase-ca.pem`, verify its issuer/fingerprint against the dashboard,
   and include that public certificate in the reviewed deployment artifact.
   Never include a private key. If Git ignores PEM files, explicitly stage only
   this reviewed public CA file. With `/backend` as the service working directory,
   use `sslrootcert=certs/supabase-ca.pem` in both database URLs; operator tools
   run elsewhere need an absolute local certificate path instead. Verify the
   file exists in both Railway pre-deploy and runtime execution. A missing,
   expired or mismatched CA must fail the connection; never switch off TLS
   verification to get a deployment through.
3. Prefer direct connections for runtime, migrations, dump and restore. On
   Railway enable outbound IPv6 and verify it in BOTH runtime and pre-deploy
   execution. On an IPv4-only runner use the **session pooler, port 5432**, with
   the exact tenant-qualified role from Connect. Do not use transaction port
   6543. The application supports both persistent connection methods explicitly.
4. In **Integrations → Data API**, turn **Enable Data API** off. Verify the
   autogenerated REST endpoint cannot expose EduG tables. Do not add Supabase
   Auth, Realtime, Edge Functions or browser database access.
5. Keep the migration/restore owner distinct from the application login. Use
   the existing target administrative connection for reviewed DDL and create a
   restricted runtime login using an interactive psql session:

   ```sql
   CREATE ROLE edug_runtime LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
     NOREPLICATION NOBYPASSRLS;
   \password edug_runtime
   ```

   `\password` prompts interactively; do not include a password in SQL text.
   If the role already exists, inspect it instead of recreating/resetting it.
   Store its connection settings only in Railway server secrets.

6. After restoring the reviewed schema, grant the runtime role only the required
   privileges. The following is for a dedicated target whose EduG objects are
   in `public`; inspect other objects before applying broad schema grants:

   ```sql
   GRANT CONNECT ON DATABASE postgres TO edug_runtime;
   GRANT USAGE ON SCHEMA public TO edug_runtime;
   REVOKE CREATE ON SCHEMA public FROM PUBLIC, edug_runtime;
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO edug_runtime;
   GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO edug_runtime;
   GRANT INSERT, UPDATE ON administrators, administrator_permissions,
     administrator_sessions, devices, policies, enrollment_tokens,
     device_credentials, device_policy_assignments,
     policy_assignment_chain_heads, policy_synchronization_chain_heads
     TO edug_runtime;
   GRANT INSERT, DELETE ON device_request_nonces TO edug_runtime;
   GRANT INSERT ON policy_revisions, device_registration_events,
     administrator_authentication_events, device_enrollment_events,
     policy_assignment_events, policy_synchronization_events TO edug_runtime;
   ```

   Verify the configured database name before using the `GRANT CONNECT` command.
   Preserve existing immutable triggers. Do not grant ownership, TRUNCATE,
   TRIGGER, schema CREATE, or UPDATE/DELETE on append-only evidence tables.
   Review/revoke existing and default access for `anon`, `authenticated`,
   `service_role` and PUBLIC on EduG objects. Default privileges depend on the
   actual migration owner; record that owner and review its `pg_default_acl`.
   Do not blanket-grant runtime DML on future tables. New migrations must include
   a reviewed runtime privilege update. Test these grants on disposable staging.

## 3. Read-only inventory

Use a secure operator shell with `SOURCE_DATABASE_URL` and
`TARGET_DATABASE_URL` already supplied by the secret manager. Use direct URLs
where available, TLS and explicit database names. Do not paste credentials into
commands. The tools do not load or print unrelated environment variables.

From `backend`, with Python 3.12 and `requirements-dev.txt` installed:

```powershell
New-Item -ItemType Directory -Path operator-evidence -ErrorAction Stop
python -m scripts.database_inventory --url-env SOURCE_DATABASE_URL --output operator-evidence/source-inventory.json
python -m scripts.database_inventory --url-env TARGET_DATABASE_URL --output operator-evidence/target-inventory.json
```

If the directory already exists, use it; never delete prior evidence. Output
files are exclusive-create and will not overwrite previous snapshots. The
directory is ignored by Git. Restrict local access: metadata remains sensitive.

These commands use read-only connections, bounded statements and a repeatable
read transaction. Reports include PostgreSQL version/size, schemas, extensions,
column definitions, migration head, keys, constraints, indexes, sequence
definitions/state, counts, triggers/functions, grants and active connection
counts. They do not export application rows, query text, passwords or URLs.
For libpq TLS, the driver confirms encryption; reports distinguish verify-full
certificate configuration from encryption-only source connections. Errors are
redacted. A permission failure, timeout, missing table or unsupported data type
means incomplete verification, never a pass. Sequence state needs stopped
writers because sequences are not frozen by the transaction snapshot.

Review these results BEFORE approving any migration operation. Do not silently
exclude unexpected schemas, extensions, tables, privileges or drift.

## 4. Independent backup and restore rehearsal

The following commands are **manual, approval-gated**, not application startup
steps. Use PostgreSQL client tools at least as new as the source server and a
target version supported by the dump. Configure non-secret libpq service names
`edug-source`, `edug-rehearsal`, `edug-target`, authentication via the approved
password file/secret manager, and verify-full TLS. Never put a full URL in CLI
arguments. Never run with shell tracing or print the password file.

1. Take a full source archive (pg_dump is read-only with respect to source data):

   ```powershell
   pg_dump --dbname=service=edug-source --format=custom --file=operator-evidence/source-rehearsal.dump --no-password
   if ($LASTEXITCODE -ne 0) { throw 'Backup failed' }
   Get-FileHash -Algorithm SHA256 operator-evidence/source-rehearsal.dump
   pg_restore --list operator-evidence/source-rehearsal.dump
   ```

2. Retain an encrypted independent copy and checksum outside both providers.
   Record role memberships, grants and extension requirements separately; a
   database dump does not include cluster roles. Do not export role passwords
   into reports. Record archive/tool versions, timestamp and operator identity.
3. Create a reviewed restore table-of-contents file from `pg_restore --list`.
   Include ALL EduG application objects, data, sequences, functions/triggers and
   `alembic_version`; exclude only reviewed provider-owned objects that must not
   overwrite Supabase infrastructure. Record every exclusion and ownership/
   privilege mapping. Do not restore source provider roles wholesale.
4. Restore into the approved EMPTY application namespace of the rehearsal target:

   ```powershell
   pg_restore --dbname=service=edug-rehearsal --no-password --no-owner --no-privileges --exit-on-error --single-transaction --use-list=operator-evidence/reviewed.list operator-evidence/source-rehearsal.dump
   if ($LASTEXITCODE -ne 0) { throw 'Restore failed; do not continue' }
   ```

   Ownership/ACL mapping is intentional and must be restored separately to the
   reviewed target roles. Do not use `--clean`, `--disable-triggers`, `dropdb`,
   schema resets or application `create_all`. If the target is not empty, stop
   and select a separate approved target. Preserve failed restore evidence.
5. Compare restored schema/data with source snapshot evidence from the same
   backup point. A live source may have changed since the archive; differences
   then require a frozen rehearsal or backup-consistent snapshot, not dismissal.
6. Preserve restored Alembic state. If it is behind the repository head, first
   compare at that historical revision with its compatible verifier, then
   rehearse pending existing upgrades on the target only. The supplied strict
   comparison tool requires the current schema/head and will deliberately
   refuse an older source; never upgrade the source just to satisfy the tool.
   Retain pre-upgrade evidence and verify deterministic data transformations.
   Missing/unknown revisions or unverified actor backfills are blockers.
7. Record restore and verification duration; use the measured result to agree
   a maintenance window. A listed archive or provider restore point is not a
   verified independent backup: an actual restore must succeed.

## 5. Configure Railway without releasing production traffic

1. Create a backend service from this repository with root directory `/backend`
   and configuration path `/backend/railway.json`. Disable automatic production
   deployments until the migration release is approved. Do not initially attach
   production credentials to a deployment that could run pre-deploy migrations.
2. Use Railpack, set `RAILPACK_PYTHON_VERSION=3.12.10` to match the verified
   baseline (review security updates separately), and verify the build log.
   Build only installs requirements; `flask --app run.py db upgrade` is the
   single pre-deploy migration command. Workers never migrate.
3. Set `APP_ENV=production`, `FLASK_DEBUG=false`, runtime
   `PRODUCTION_DATABASE_URL`, owner `MIGRATION_DATABASE_URL`, and verified CA
   trust. Both URLs must identify the same project AND database. Provision the
   CA at a stable read-only path if the platform trust store does not contain it.
4. Transfer valid, distinct existing `SECRET_KEY`, `JWT_SECRET_KEY`,
   `ADMIN_AUDIT_PSEUDONYM_KEY`, `POLICY_SYNC_AUDIT_KEY`, required
   `PAIRING_TOKEN_PEPPER` and its version securely. Preserve actual enrollment
   mode/admin-enabled settings. Never invent the deployed mode from examples.
5. Configure reachable shared Redis using `REDIS_URL`; reuse the existing
   service if secure cross-provider access is supported, otherwise provision
   the equivalent Railway Redis service. Use private networking or verified TLS
   for public Redis. This preserves an existing dependency; memory fallback is
   forbidden. The application fails startup/readiness if Redis is unavailable.
6. Set `ADMIN_FRONTEND_ORIGINS` to exact HTTPS origins, comma-separated, with
   no trailing slash. Set pool size 3/overflow 2 and sync rate `60 per minute`
   unless verified source settings differ. Configure `SENTRY_DSN` if used.
7. Start command is `gunicorn --config gunicorn.conf.py run:app`; Railway supplies
   PORT. Keep one worker, four threads and one replica initially. Budget five
   connections per instance plus deployment overlap, migrations and platform
   services against actual Supabase limits. Do not enable sleep/serverless mode
   for this persistent deployment.
8. Healthcheck is `/api/v1/ready`; liveness remains `/api/v1/health`. Validate
   HTTPS, allowed/disallowed CORS, one-hop proxy behavior, forged forwarded
   headers, raw signed request targets, shared rate limiting, graceful shutdown,
   log privacy and Sentry delivery in staging.
9. Do not run SQLite-backed testing configuration in production. Test production
   startup with real isolated PostgreSQL and Redis. Staging business smoke tests
   write audit records: never point them at the protected source database.

## 6. Final maintenance and explicit approval

1. Obtain recorded cutover approval after all tests, rehearsal, secret hygiene,
   Android endpoint/offline evidence and rollback checks pass.
2. Stop every source writer: all web instances, sync traffic, CLI jobs, schedulers
   and migration hooks. Policy-sync GET requests and authentication can write
   audit rows. Never assume a GET-only endpoint is a read-only workload.
3. Confirm writer quiescence. Capture final fingerprints and audit verification:

   ```powershell
   python -m scripts.database_inventory --url-env SOURCE_DATABASE_URL --output operator-evidence/source-final.json --fingerprints --verify-audit --writers-stopped
   ```

   `--writers-stopped` is an operator attestation, not a command to stop writers.
   The tool makes no production configuration changes.
4. Create/checksum/independently retain the final backup. Restore using the
   rehearsed reviewed procedure into the approved target, with its writers
   stopped. Apply only the previously rehearsed pending migrations, if any.
5. At matching schema state, verify the target and compare:

   ```powershell
   python -m scripts.database_inventory --url-env TARGET_DATABASE_URL --output operator-evidence/target-final.json --fingerprints --verify-audit --writers-stopped
   python -m scripts.compare_database_inventories operator-evidence/source-final.json operator-evidence/target-final.json
   ```

   The comparator checks all public-table fingerprints, counts, columns,
   constraints/indexes, sequence state/definitions, row-security flags, triggers,
   EduG functions and audit results. It does not authorize cutover. Review
   extensions, other schemas and intentional role/grant mappings separately.
   Never edit snapshot files to make comparison pass.
6. Verify database head, runtime privileges, TLS, readiness and limits; route
   the approved stable API hostname to Railway. Do not rewrite signed paths.
7. Enable target writers only after the gates pass. Run approved traceable
   production smoke operations and keep their evidence; never delete audit rows
   produced by verification. Confirm Android reconnects without clearing cached
   policy on network failures and handles queued work through its verified APIs.
8. Monitor readiness, 5xx/429, authentication, DB connections/latency, Redis and
   audit persistence. Railway deployment healthchecks do not replace ongoing
   monitoring. Retain source and backups until an explicit retention decision.

## 7. Rollback

Before target writes: stop Railway, preserve target evidence, restore the
verified old routing/application/source combination and resume source writers.
After target writes: never switch silently to the stale source. Stop writers,
preserve target data/evidence and deploy a compatible release against Supabase,
or obtain approval for a verified reverse transfer preserving all new records.
Keep the recorded Supabase-compatible rollback release and its requirements.
Never downgrade forensic migrations or
merge divergent audit chains automatically. Source deletion and history rewrites
require separate explicit owner approval.
